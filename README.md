# MAX Найм

Сервис внутри MAX, который проводит владельца небольшого бизнеса от «нужен сотрудник» до назначенного собеседования — без объявлений на job boards, разбора сотен откликов и переписки о времени встречи.

## Для кого

Владелец или управляющий кафе, магазина, салона — бизнес на 1–10 человек. Отдельного HR нет, наймом занимается сам собственник между всеми остальными делами. Пилот — Москва, HoReCa: бариста, официанты, администраторы.

## Проблема

Нанять бариста сегодня — это написать вакансию, оплатить размещение, получить поток откликов, где половина людей не готовы работать в нужном графике или вообще не выйдут, каждому написать, с каждым согласовать время. На это уходят дни, которых у владельца точки нет.

## Как это работает

**Работодатель** открывает MAX Найм, нажимает «Найти сотрудника» и описывает, кто ему нужен: должность, район, деньги, график, когда нужно выйти. Для каждого условия отмечает, обязательное оно или желательное. Вакансия публикуется, получает ссылку, которой можно поделиться.

**Кандидат** нажимает «Ищу работу», заполняет короткий профиль — без резюме — и получает ленту подходящих вакансий. Понравилась — свайп вправо, это отклик. Дальше 3–4 коротких вопроса: график, район, дата выхода, опыт.

**Система** проверяет объективные условия и показывает работодателю уже отобранного кандидата — одинаково оформленной карточкой: опыт, ожидания, график, когда готов выйти, ответы на вопросы и какие условия совпали.

**Решение** — одно нажатие: отклонить или пригласить. Если кандидат уже откликнулся, а работодатель пригласил — возникает взаимный интерес, кандидат выбирает время из слотов работодателя, и обоим приходит подтверждение прямо в MAX.

```text
Нужен сотрудник → вакансия → отклик → отбор → карточка
        → решение → взаимный интерес → выбор времени
        → Интервью назначено
```

## Что отличает

**Отбор, а не поток.** Работодатель видит не все отклики, а тех, кто уже прошёл проверку по обязательным условиям.

**Честные причины вместо процентов.** Никаких «93% совпадение». Карточка говорит конкретно: «5 из 5 обязательных условий» и какие именно.

**Объективные критерии.** Решение строится на локации, графике, зарплате, дате выхода, опыте и нужных документах. Фото, пол, возраст (вне требований закона) и оценки вроде «харизматичный» для автоматического отбора не используются.

**Всё внутри MAX.** Отдельного приложения, регистрации и паролей нет — вход через MAX, уведомления приходят туда же.

**Кандидату не нужно резюме.** Короткий профиль и несколько ответов — достаточно, чтобы попасть к работодателю.

## Что дальше

Дальше продукт учится понимать вакансию с голоса или свободного текста, скрывает имя и фото до взаимного интереса, объясняет каждое совпадение, запоминает причины отказов и подсказывает кандидатов из резерва, показывает владельцу простую доску найма и воронку: сколько откликов, сколько дошло до интервью и за какое время.

## Состав и архитектура

```text
MAX (клиент, бот)
   │  Mini App (WebView)                    │  webhook /webhook/max
   ▼                                        ▼
┌──────────────────────────── nginx ─────────────────────────────┐
│ статика frontend (React) │ /api, /webhook, /health → backend    │
└─────────────────────────────────────────────────────────────────┘
                                   │
                    ┌──────────────┴──────────────┐
                    ▼                             ▼
             backend (FastAPI)              PostgreSQL 16
      REST API + бот maxapi + миграции      (основная БД)
                    │
                    ├── Redis 7 (кэш, опционален)
                    ├── storage/ (volume: аватарки, резюме)
                    └── MAX Bot API, GigaChat, YandexGPT (внешние)
```

| Компонент | Технологии | Контейнер |
|---|---|---|
| Frontend | React, TypeScript, Vite, MAX UI, MAX Bridge; собирается внутри образа nginx | `nginx` |
| Backend | Python 3.12, FastAPI, Pydantic v2, Tortoise ORM + aerich, `maxapi[fastapi]`, Uvicorn | `backend` |
| БД | PostgreSQL 16 | `postgres` |
| Кэш | Redis 7 (без него приложение работает напрямую с БД) | `redis` |

Backend обслуживает и Mini App (REST под `/api`), и бота MAX (webhook) — это одно
приложение. Личность пользователя определяется только серверной сессией после
проверки подписи MAX `initData` (HMAC-SHA256); бизнес-статусы меняет только backend.
Подробности — в [docs/tech-spec-v2.2.md](docs/tech-spec-v2.2.md),
[docs/api-contracts.md](docs/api-contracts.md) и [backend/README.md](backend/README.md).

## Запуск через Docker

Нужны Docker с Compose v2.24+ и свободные порты (см. ниже). Все локальные
компоненты (nginx с frontend, backend, PostgreSQL, Redis) поднимаются **одной командой**
из корня репозитория:

```bash
docker compose up --build
```

Контейнер backend сам применяет миграции, загружает справочник навыков и
запускает Uvicorn. Стек стартует и без файла `.env` — на значениях по
умолчанию (без MAX-токенов бот и уведомления отключены, вход через MAX работать
не будет). Сборка образов занимает 1–3 минуты без учёта первой загрузки базовых
образов.

Проверка: `http://localhost:8080/health` возвращает `{"status": "ok"}`.

Режим разработки (код с reload, доступ к backend, БД и Redis с хоста, HTTPS):

```bash
cp .env.example .env
docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build
```

Остановка и повторный запуск:

```bash
docker compose down              # остановить; данные (БД, файлы) сохраняются
docker compose up -d             # запустить снова, без пересборки
docker compose up -d --build     # запустить с пересборкой после изменения кода
docker compose down -v           # остановить и УДАЛИТЬ данные (чистый старт)
```

## Переменные окружения

Файл-образец — [.env.example](.env.example) (без рабочих токенов и паролей):
`cp .env.example .env`, затем заполнить значения. `.env` в Git не попадает.

| Переменная | Обязательна | Назначение |
|---|---|---|
| `APP_URL` | в production | публичный адрес приложения (ссылки в уведомлениях, webhook) |
| `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | сменить пароль | доступ к PostgreSQL; пароль без символов `@ : / ? # %` |
| `SESSION_SECRET` | в production | секрет серверных сессий |
| `MAX_BOT_TOKEN` | для входа через MAX и бота | токен бота: проверка подписи `initData` и Bot API |
| `MAX_WEBHOOK_SECRET` | для бота | секрет webhook'а, **не** равен токену бота |
| `MAX_BOT_USERNAME` | для бота | имя бота без `@` (кнопка «открыть приложение») |
| `BOT_ENABLED` | нет | `false` выключает отправку сообщений в MAX, остальное работает |
| `AI_PROVIDER_ORDER`, `GIGACHAT_AUTH_KEY`, `YANDEX_API_KEY`, `YANDEX_FOLDER_ID` | нет | AI-функции (P1); без них доступен ручной ввод |
| `HTTP_PORT`, `HTTPS_PORT` | нет | порты nginx на хосте |
| `NPM_REGISTRY` | нет | зеркало npm для сборки frontend |
| `REDIS_URL` | нет | пусто — кэш выключен |

Полный список с комментариями и значениями по умолчанию — в `.env.example`.

## Порты

| Порт на хосте | Сервис | Когда доступен |
|---|---|---|
| `8080` (`HTTP_PORT`) | nginx: frontend, `/api`, `/webhook`, `/health` | всегда |
| `8443` (`HTTPS_PORT`) | nginx по HTTPS (самоподписанный сертификат) | только dev-режим |
| `8000` | backend напрямую, документация `/docs` | только dev-режим |
| `5432` | PostgreSQL | только dev-режим |
| `6379` | Redis | только dev-режим |

## Зависимости

Версии зафиксированы в lock-файлах:

- backend — [backend/pyproject.toml](backend/pyproject.toml) и [backend/uv.lock](backend/uv.lock) (менеджер `uv`);
- frontend — [frontend/package.json](frontend/package.json) и [frontend/package-lock.json](frontend/package-lock.json).

Образы: `python:3.12-slim`, `node:22-alpine` (только для сборки), `nginx:1.27-alpine`,
`postgres:16-alpine`, `redis:7-alpine`.

## Внешние сервисы и интеграции

| Сервис | Зачем | Без него |
|---|---|---|
| MAX (клиент, Bot API) | запуск Mini App, вход через `initData`, уведомления, webhook бота | Mini App открывается только внутри MAX; без токена вход невозможен |
| GigaChat, YandexGPT | разбор вакансии из текста и голоса (P1) | обязательный маршрут не зависит от AI, доступен ручной ввод |

Ключи обоих сервисов выдаются в их личных кабинетах — в репозитории их нет.
Других сервисов вне Docker для проверки не нужно. Webhook MAX работает только по
HTTPS с публичного адреса, поэтому локально не регистрируется.

## Работа с данными

- **PostgreSQL** (volume `pgdata`) — пользователи, профили, вакансии, отклики, слоты, интервью, журнал уведомлений. Схема создаётся миграциями `aerich` при старте backend.
- **Справочник навыков** (около 2 тысяч записей) загружается из `backend/app/skills/data/` при каждом старте; повторная загрузка ничего не дублирует.
- **Файлы** (аватарки, резюме) — каталог `storage/` в volume `storage`.
- **Redis** (volume `redisdata`) — только кэш, потерять его безопасно.
- Данные переживают `docker compose down` и пересборку; полностью очищаются только `docker compose down -v`.

## Тестовые данные

Готовых демо-записей в базе нет: продукт создаёт данные сам, а вход возможен
только через MAX. Для проверки без клиента MAX есть три способа; первые два
работают с синтетическими пользователями (`999000001`, `999000002`), реальных
людей они не затрагивают.

1. **Сквозной прогон маршрута на живом приложении** — скрипт сам подписывает
   `initData` токеном из окружения, проходит весь путь до `Interview scheduled`
   и **удаляет свои данные** после прогона:

   ```bash
   docker compose -f docker-compose.yml -f docker-compose.dev.yml exec backend python scripts/dev_check.py
   ```

   Токен может быть любым непустым (например, `MAX_BOT_TOKEN=test_token` в `.env`):
   подпись проверяется тем же значением. Реальный токен нужен, только чтобы
   уведомления дошли в MAX; при `BOT_ENABLED=false` они остаются в статусе `pending`.

2. **Ручные запросы к API** — подписанная `initData` для `/docs` и для frontend
   вне MAX (значение кладётся в `frontend/.env.local` как `VITE_DEV_INIT_DATA`):

   ```bash
   docker compose -f docker-compose.yml -f docker-compose.dev.yml exec backend python scripts/dev_check.py --init-data
   ```

3. **Автотесты** (`cd backend && uv run pytest`) используют отдельную БД
   `<db>_test`, которую сами создают и удаляют; данные разработки не
   затрагиваются (см. [backend/README.md](backend/README.md)).

## Пошаговый сценарий проверки

Автоматически, без MAX:

1. `cp .env.example .env`; в `.env` указать `MAX_BOT_TOKEN=test_token` и `BOT_ENABLED=false`.
2. `docker compose -f docker-compose.yml -f docker-compose.dev.yml up --build -d`.
3. Открыть `http://localhost:8000/health` — ответ `{"status": "ok"}`; `http://localhost:8080` отдаёт frontend.
4. Выполнить `dev_check.py` (команда выше). Ожидается итог `провалено 0`.

Вручную в MAX (нужны реальный бот: `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`,
`MAX_BOT_USERNAME` и публичный HTTPS-адрес в `APP_URL`):

1. Открыть Mini App из бота, выбрать роль работодателя («Найти сотрудника»).
2. Создать вакансию: должность, район, оплата, график, дата выхода; отметить обязательные условия; опубликовать.
3. Добавить слоты собеседований.
4. Со второго аккаунта MAX открыть Mini App, выбрать «Ищу работу», заполнить короткий профиль.
5. В ленте найти вакансию, откликнуться свайпом вправо, ответить на вопросы.
6. У работодателя появится карточка кандидата — пригласить его.
7. Кандидату придёт уведомление в MAX; он выбирает свободный слот.
8. Обоим приходит подтверждение, отклик получает статус `interview_scheduled`.

## Примеры ожидаемого поведения

- Новый пользователь после входа не имеет роли и сначала выбирает её.
- Карточка кандидата показывает совпадения («5 из 5 обязательных условий»), а не процент.
- Кандидат, не прошедший обязательное условие, не попадает к работодателю.
- Занятый слот при бронировании возвращает `409 Conflict`; повторное бронирование того же слота тем же кандидатом не создаёт второе интервью.
- Ошибка отправки уведомления в MAX не отменяет назначенное собеседование.
- Запрос на `/webhook/max` без верного `X-Max-Bot-Api-Secret` получает `403`.

## Известные ограничения

- Mini App работает только внутри MAX; в обычном браузере нужна `VITE_DEV_INIT_DATA`.
- Без токена бота нет ни входа, ни уведомлений.
- Webhook регистрируется только в `APP_ENV=production` по HTTPS; локально он не подключается.
- Фоновой очереди повторов уведомлений нет: повторы выполняются в пределах запроса.
- AI-функции (P1) требуют ключей GigaChat/YandexGPT и не входят в обязательный маршрут.
- Пилот рассчитан на Москву и HoReCa.
- Локальный HTTPS использует самоподписанный сертификат: браузер предупредит о нём.
