# Навигатор — мини-приложение для мессенджера MAX

Образовательный сервис для хакатона MAX × Минобрнауки, трек 2 «Образовательные
решения». Мини-приложение открывается внутри мессенджера MAX и закрывает восемь
функциональных блоков плюс профиль пользователя: профориентационный тест, подбор
вуза по баллам ЕГЭ, трекер конкурсных списков, расписание и дедлайны, вопросы
старшекурсникам, рейтинг активности, точки питания рядом с вузом, поддержка.

Требования — в [`docs/`](docs/), они первичны. Что уже сделано и что следующее —
в [`PLAN.md`](PLAN.md). Почему код устроен именно так — в
[`DECISIONS.md`](DECISIONS.md). Конвенции разработки — в
[`CONTRIBUTING.md`](CONTRIBUTING.md). Неотменяемые инварианты продукта — в
[`CLAUDE.md`](CLAUDE.md).

## Запуск

```bash
cp .env.example .env
docker compose up --build        # бэкенд
pnpm install && pnpm --filter miniapp dev   # фронтенд на хосте
```

Или через make:

```bash
make up          # бэкенд в docker
make dev-front   # мини-приложение на http://localhost:5173
```

**Dev-сервер Vite по умолчанию в docker не поднимается.** Он объявлен
отдельным сервисом `miniapp-dev` в профиле `frontend`: Vite в контейнере даёт
медленный HMR через смонтированный том и пересборку образа на каждое изменение
зависимостей. Кому удобнее прежний вариант — `make up-all` или
`docker compose --profile frontend up`.

**Собранная статика при этом поднимается всегда** — сервисом `miniapp`, за
которым стоит nginx-точка входа. Это тот же набор контейнеров, что работает на
стенде, поэтому первый `up --build` заметно дольше: собирается продовый бандл.

**nginx занимает 80 и 443.** Если порты заняты, поменяйте `HTTP_PORT` и
`HTTPS_PORT` в `.env` — и заходите сразу по https: на нестандартном порту
редирект с http ведёт на `https://<хост>` без порта, потому что внешний порт
изнутри контейнера не виден. Сертификат локально самоподписанный — nginx выпускает
его сам при старте и пишет об этом в лог, поэтому браузер ругается на
«ненадёжное соединение». Так и должно быть: настоящий сертификат нужен только
стенду и приходит туда переменными `TLS_CERT` и `TLS_KEY`.

Что поднимется:

| Сервис | Адрес | Что это |
|---|---|---|
| `nginx` | https://localhost | точка входа: фронт и API на одном домене |
| `miniapp` | только внутри docker-сети | собранная статика мини-приложения, её отдаёт nginx |
| `miniapp-dev` | http://localhost:5173 | dev-сервер Vite с HMR (только с профилем `frontend`) |
| `core-api` | http://localhost:8010/docs | Core API: модульный монолит, FastAPI + Tortoise |
| `admin` | http://localhost:8001 | админка: очереди обращений и спорных вопросов (У26) |
| `worker` | — | Celery-воркер фоновых задач |
| `beat` | — | планировщик Celery Beat |
| `ai-gateway` | только внутри docker-сети | единственная точка вызова LLM |
| `postgres` | localhost:5432 | все бизнес-данные |
| `redis` | localhost:6379 | кэш внешних API и брокер очередей |

Перед стартом приложения отрабатывают два разовых шага: `migrate` приводит
схему базы к моделям, `seed` заливает справочники — вузы, направления, вопросы
теста, программы приёмной кампании и расписания групп. Оба идемпотентны и
выполняются при каждом подъёме; справочники можно залить и отдельно —
`make seed`.

**Админке нужен `ADMIN_PASSWORD`** в `.env`: без него она не поднимается. В её
очередях лежат тексты обращений пользователей, и открытой она быть не может.
Доступ — HTTP Basic, логин по умолчанию `admin` (уточнение У26, тех. ТЗ 9.4).

**Мини-приложение ходит в API через прокси dev-сервера**, а не по адресу
`localhost:8010`: браузеру хватает одного порта 5173, и CORS не нужен. Порт
Core API публикуется только для разработчика — открыть `/docs` и сходить
`curl`. Если он занят, задайте свой в `CORE_API_PORT`; на работу приложения это
не влияет.

AI Gateway наружу не публикуется намеренно: это внутренний сервис (тех. ТЗ 5).
Порты Postgres и Redis открыты только на `127.0.0.1` — для `psql` и `redis-cli`
разработчика.

## Проверки

```bash
make check      # линтеры, типы и все тесты, кроме e2e
make test-e2e   # Playwright на мобильном и десктопном профиле (ТЗ 0.2)
```

Разработка без docker — `make dev-core`, `make dev-front` и остальные цели
`make dev-*`; полный список команд показывает `make`.

## CI/CD

Проверки — [`.github/workflows/ci.yml`](.github/workflows/ci.yml), выкладка —
[`.github/workflows/deploy.yml`](.github/workflows/deploy.yml).

CI гоняется на каждом pull request и на каждом пуше в `main`, пятью
параллельными заданиями: бэкенд (линтеры, типы, тесты на настоящих Postgres
и Redis, проверка что миграции не разошлись с моделями), фронтенд, совпадение
типов фронта со схемой бэкенда, e2e на обоих профилях устройств и сборка всех
четырёх образов.

**На pull request идут не все пять.** Быстрые — бэкенд, фронтенд, образы —
всегда; медленные — e2e и сверка типов со схемой — только на `main` и по
ручному запуску. Размен честный: поломку e2e теперь видно после слияния,
а не до. Но незамеченной она не останется и на стенд не уедет — деплой
подписан на **успешное** завершение CI, поэтому красный e2e на `main`
останавливает выкладку ровно так же, как раньше останавливал слияние.

Деплой подписан на **завершение** CI, а не на пуш: обогнать проверки он не
может. Публикуется только `main` и только тот коммит, который прошёл CI, —
не «последний в ветке». Образы уезжают в GHCR с тегом коммита и меткой
`org.opencontainers.image.revision`.

**На сервер отсюда никто не ходит.** Входящий SSH с раннеров GitHub до стенда
не доходит — измерено, решение Р71. Поэтому связь развёрнута: таймер systemd на
сервере раз в минуту проверяет реестр и сам поднимает новую сборку. Установка
и диагностика — [`infra/deploy/README.md`](infra/deploy/README.md).

**Публикации образов секреты не нужны** — хватает встроенного `GITHUB_TOKEN`.
Секреты в Settings → Secrets and variables → Actions остались вот для чего:

| Секрет | Кому нужен |
|---|---|
| `MAX_MINI_APP_DEPLOY_DOMAIN` | шагу `verify`, чтобы дёрнуть `/health` после публикации |
| `MAX_MINI_APP_DEPLOY_HOST`, `..._USER`, `..._SSH_KEY`, `..._KNOWN_HOSTS` | только пробе `Диагностика SSH` — она проверяет, не починилась ли связь |

На сервере до первого деплоя нужен Docker с плагином compose, каталог
`/opt/navigator` и в нём `.env` — по образцу [`.env.example`](.env.example).
Выкладка этот файл не трогает: пароли стенда не должны проходить через git
и через логи Actions. Установка таймера — в
[`infra/deploy/README.md`](infra/deploy/README.md).

Стенд поднимается с `ENVIRONMENT=staging` и `MOCK_AUTH=true` — пока алгоритм
проверки подписи `initData` не сверен с документацией MAX (тех. ТЗ 9.7). Это
значит, что стенд демонстрационный: любой запрос может назвать себя любым
пользователем, и публичной ссылкой на него делиться не стоит.

### Выкладка на PaaS-панель (Timeweb и подобные)

Основной путь — Docker и таймер выше. Панель нужна там, где Docker недоступен;
она умеет только `pip install -r requirements.txt` и `npm run build`, поэтому:

**Фронтенд** (сборка Vite, статика):

| Поле панели | Значение |
|---|---|
| Версия Node | `22` |
| Команда сборки | `npm i -g pnpm@10.33.0 && pnpm install --frozen-lockfile && pnpm --filter miniapp build` |
| Директория сборки | `apps/miniapp/dist` |
| Путь до проекта | корень репозитория (там `pnpm-workspace.yaml` и локфайл) |
| Переменные | `VITE_API_BASE_URL=https://<домен API>`, `VITE_MOCK_MAX_USER_ID=mock-user-1` |

`VITE_*` попадают в бандл на этапе сборки: смена адреса API требует пересборки.
Пустой `VITE_API_BASE_URL` работает только при общем домене с API — режим
same-origin в compose держится на прокси dev-сервера, которого в панели нет.
Отдельно нужен SPA-фолбэк на `index.html`, иначе обновление страницы на любом
маршруте даст 404 (закольцованная навигация, ТЗ 1.1).

**Бэкенд** — `apps/core/requirements.txt` и `apps/ai-gateway/requirements.txt`,
команды в README соответствующего сервиса. Это не один процесс: Core API,
Celery-воркер, Celery Beat, админка и AI Gateway запускаются раздельно, плюс
`aerich upgrade` до первого старта. Наружу публикуется только фронт и Core API;
админка и AI Gateway остаются на `127.0.0.1`.

**Требования файлов не отменяют `uv`.** `requirements.txt` производные от
`uv.lock`, генерируются `make requirements`, расхождение ловит CI (решение Р75).

## Архитектура

```
┌──────────────────┐      ┌────────────────────┐      ┌─────────────────┐
│  React Mini App  │─────▶│  Core API          │─────▶│  AI Gateway     │
│  MAX Mini Apps   │      │  FastAPI+Tortoise  │      │  YandexGPT /    │
└──────────────────┘      │  PostgreSQL        │      │  GigaChat       │
                          └─────────┬──────────┘      └─────────────────┘
                                    │ ставит задачи
                                    ▼
                          ┌────────────────────┐
                          │  Worker            │
                          │  Celery + Beat     │───▶ внешние API
                          │  Redis (broker)    │     (hh.ru, Карты,
                          └────────────────────┘      сайты вузов)
```

Модульный монолит с двумя вынесенными сервисами. Разделение оправдано
паттернами отказа, а не модностью: LLM-вызовы — самая нестабильная по времени
ответа часть системы, фоновые задачи ходят во внешние источники, которые умеют
подвисать. Подробнее — тех. ТЗ, раздел 1.

Структура каталогов и правила границ доменов — в
[`CONTRIBUTING.md`](CONTRIBUTING.md).

## Состояние работ

Что сделано, что следующее и чем оно заблокировано — в [`PLAN.md`](PLAN.md).
Здесь это специально не дублируется: два места с состоянием расходятся на
первой же неделе, и непонятно, какому верить.

### Что известно про платформу MAX

Официальная документация `dev.max.ru` закрыта сетевой политикой окружения
разработки: egress-прокси отвечает 403 на CONNECT. Поэтому формат `initData`,
алгоритм проверки подписи, API нативной кнопки «назад» и имя npm-пакета SDK
мини-приложений первичными источниками **не подтверждены** — см. тех. ТЗ 9.7.

Разработку это не блокирует: режим `MOCK_AUTH` открывает приложение в обычном
браузере, а весь доступ к платформе изолирован в один модуль-адаптер. Проверка
подписи пишется сразу и включается снятием флага, когда документация станет
доступна.
