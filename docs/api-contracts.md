# Зафиксированные API-контракты

Рабочий документ команды: контракты эндпоинтов, которые уже реализованы на
backend. Frontend не должен угадывать формат, backend не меняет контракт без
согласования.

Источник истины по полям и статусам — [tech-spec-v2.2.md](tech-spec-v2.2.md).
Здесь только то, что нужно для интеграции.

Общие правила:

- все эндпоинты живут под префиксом `/api`;
- пользователь определяется серверной сессией (cookie), `user_id` в теле
  запроса игнорируется;
- ошибка возвращается как `{"error": {"code": "...", "message": "...", "details": ...}}`;
- `401` — нет сессии, `403` — не та роль, `404` — объекта нет, `409` — конфликт
  состояния, `422` — ошибка валидации (раздел 57 тех-доки).

## POST /api/auth/max

Auth: не требуется — этим запросом сессия и создаётся.

Request:

```json
{"init_data": "auth_date=...&user=...&hash=..."}
```

`init_data` — **исходная строка** `window.WebApp.initData` целиком, без
пересборки на frontend. Отправлять вместо неё `user_id` нельзя: личность
подтверждается только подписью (раздел 6).

Response 200:

```json
{
  "user": {
    "user_id": 100500,
    "first_name": "Иван",
    "last_name": "Петров",
    "username": "ivan_petrov",
    "language_code": "ru",
    "role": null,
    "has_avatar": false,
    "avatar_updated_at": null
  },
  "current_step": "role_selection",
  "application_id": null
}
```

Ответ ставит HTTP-only cookie сессии. Все остальные запросы идут с ней;
`user_id` в теле запроса backend не принимает нигде.

`role` у нового пользователя — `null`: авторизация роль не назначает
(раздел 8).

`current_step` — шаг, на который нужно вернуть пользователя при повторном
открытии Mini App (раздел 7):

```text
role_selection      роль не выбрана
candidate_profile   кандидат без профиля
feed                кандидат с профилем без активного отклика
application_status  кандидат с активным откликом (+ application_id)
vacancy_create      работодатель без вакансий
employer_home       работодатель с вакансиями
```

`application_id` заполняется только для шага `application_status`.

Повторная авторизация не перезаписывает изменённые пользователем `first_name`
и `last_name` данными MAX.

Errors:

```text
401 invalid_init_data — подпись не сошлась или `auth_date` слишком старый
422 validation_error  — пустая строка `init_data`
429 rate_limited      — слишком часто; details: {"retry_after_seconds": ...}
```

## GET /api/users/me/avatar

Auth: любая роль.

Отдаёт файл аватарки **текущего** пользователя. Чужой файл получить нельзя:
путь строится из сессии, а не из параметров запроса.

Response 200: содержимое файла.

Errors:

```text
401 unauthorized     — нет сессии
404 avatar_not_found — аватарка не установлена
```

## PATCH /api/users/me/avatar

Auth: любая роль. Тело — `multipart/form-data`, поле `file`.

Устанавливает аватарку, а если она уже есть — заменяет. Отдельного `POST` нет
(раздел 27). Старый файл удаляется после успешного сохранения нового.

Тип определяется по содержимому файла, а не по имени и заголовку: переименованный
`.exe` не пройдёт. Допустимые типы и предел размера задаются настройками
`AVATAR_ALLOWED_MIME_TYPES` и `AVATAR_MAX_SIZE_BYTES`.

Response 200: объект `user` с обновлёнными `has_avatar` и `avatar_updated_at`.

Errors:

```text
401 unauthorized          — нет сессии
422 empty_file            — пустой файл
422 file_too_large        — больше AVATAR_MAX_SIZE_BYTES
422 unsupported_file_type — содержимое не входит в белый список типов
422 validation_error      — файл не передан
```

## PATCH /api/candidate/profile

Auth: `candidate`.

Создаёт профиль при первом обращении, дальше меняет переданные поля.
Отдельного `POST` нет: профиль связан с пользователем 1:1.

Request (все поля необязательные):

```json
{
  "desired_role": "Бариста",
  "city": "Москва",
  "salary": "70000.00",
  "schedule": "full_time",
  "experience_months": 24,
  "available_from": "2026-10-01"
}
```

Правила полей:

| Поле | Ограничения | Поведение при `null` |
|---|---|---|
| `desired_role` | строка 1–255, обязательна при создании | нельзя очистить |
| `city` | строка до 255 | очищает поле |
| `salary` | число ≥ 0, не больше 2 знаков после запятой, до 12 цифр | очищает поле |
| `schedule` | строка до 100 | очищает поле |
| `experience_months` | целое 0–1200 | очищает поле |
| `available_from` | дата `YYYY-MM-DD` | очищает поле |

Поле, которого нет в теле запроса, не меняется. Пустая строка в `city` и
`schedule` равна `null`. Зарплата всегда возвращается с двумя знаками после
запятой.

Response 200: тот же объект, что у `GET /api/candidate/profile`.

Errors:

```text
401 unauthorized          — нет сессии
403 role_not_selected     — роль ещё не выбрана
403 wrong_role            — роль не candidate
422 desired_role_required — профиля нет, а желаемая должность не передана
422 validation_error      — значение поля не проходит ограничения
```

Изменение профиля не трогает `screening_answers`: ответы первичного отбора
привязаны к отклику и остаются историческими.

## POST /api/vacancies

Auth: `employer`. `employer_id` в теле не принимается — берётся из сессии.

Request:

```json
{
  "title": "Бариста в центре",
  "company_name": "Кофейня «Утро»",
  "description": "Ищем бариста в дружную команду.",
  "location": "Москва",
  "salary_min": "60000",
  "salary_max": "90000",
  "schedule": "full_time",
  "status": "draft",
  "criteria": [
    {"type": "location", "required": true, "value": {"city": "Москва"}},
    {"type": "experience", "required": false, "value": {"min_months": 12}, "weight": "0.80"}
  ],
  "questions": [
    {
      "question": "Есть ли действующая медкнижка?",
      "type": "boolean",
      "required": true,
      "validation_rules": {"must_equal": true}
    }
  ]
}
```

Обязателен только `title`. `status` — `draft` (по умолчанию) или `published`;
`closed` при создании не принимается. Публикация сразу при создании возможна,
если заполнено всё, что требует раздел 29 (см. ниже).

`company_name` и `description` — не из тех-доки (раздел 15 их не
перечисляет), добавлены отдельным продуктовым решением. Оба необязательны и
**не входят** в проверку публикации — раздел 29 фиксирует ровно 4
обязательных поля закрытым списком, это решение его не расширяет.

`criteria` (до 20) и `questions` (до 6) создаются тем же запросом. Формат
`value` и `validation_rules` — в конце документа; условие, которое подбор не
сможет прочитать, отклоняется, а не сохраняется молча. Порядок вопросов
задаёт сам список: `sort_order` в теле не принимается и проставляется с 1.

Раздел 18: в P0 вопросов 3–4, верхняя граница P1 — 6. Backend разрешает до 6,
продуктовое ограничение остаётся за интерфейсом.

**Лимит черновиков (не из тех-доки).** У одного работодателя не может быть
больше `VACANCY_DRAFT_LIMIT` (по умолчанию 5) вакансий одновременно в статусе
`draft`. Считаются только черновики — публикация одного из них сразу
освобождает место для нового; создание сразу со `status: "published"` лимит
не расходует.

Response 201: объект вакансии (см. `GET /api/vacancies/{id}`).

Errors:

```text
401 unauthorized                — нет сессии
403 role_not_selected           — роль ещё не выбрана
403 wrong_role                  — роль не employer
409 draft_limit_reached         — исчерпан лимит черновиков;
                                  details: {"limit": 5}
422 vacancy_incomplete          — публикация без обязательных данных;
                                  details: {"missing": ["location", "salary", ...]}
422 vacancy_criteria_invalid    — details: [{"index": 0, "type": "...", "code": "...", "details": {...}}]
422 screening_questions_invalid — details: [{"index": 0, "code": "...", "details": {...}}]
422 validation_error            — длина, тип, отрицательная зарплата,
                                  `salary_min > salary_max`, `status: "closed"`
```

## GET /api/vacancies/{id}

Auth: `employer` или `candidate`.

Работодатель открывает **только свою** вакансию в любом статусе. Кандидат —
опубликованную или ту, на которую уже откликнулся (иначе закрытая вакансия
исчезла бы из его же отклика). Всё остальное — `404`.

Response 200:

```json
{
  "id": 4,
  "employer_id": 100500,
  "title": "Бариста в центре",
  "company_name": "Кофейня «Утро»",
  "description": "Ищем бариста в дружную команду.",
  "location": "Москва",
  "salary_min": "60000.00",
  "salary_max": "90000.00",
  "schedule": "full_time",
  "status": "published",
  "public_token": "0Kb1x...",
  "public_url": "https://example.com/v/0Kb1x...",
  "applications_count": 3,
  "criteria": [
    {"id": 7, "type": "location", "required": true, "value": {"city": "Москва"}, "weight": null}
  ],
  "questions": [
    {
      "id": 11,
      "question": "Есть ли действующая медкнижка?",
      "type": "boolean",
      "required": true,
      "sort_order": 1,
      "validation_rules": {"must_equal": true}
    }
  ],
  "created_at": "2026-09-22T10:00:00Z",
  "updated_at": "2026-09-22T10:00:00Z"
}
```

Кандидату `public_token`, `public_url` и `applications_count` приходят как
`null`, а в `validation_rules` не попадает `must_equal`: зная отсекающее
условие, ответ можно подогнать.

`public_url` — ссылка вида `{APP_URL}/v/{public_token}` (раздел 15). Токен
выдаётся один раз при первой публикации и при повторной не меняется.

Errors:

```text
401 unauthorized      — нет сессии
403 role_not_selected — роль ещё не выбрана
404 vacancy_not_found — вакансии нет, она чужая или недоступна этой роли
```

## PATCH /api/vacancies/{id}

Auth: `employer`, вакансия должна принадлежать текущему пользователю.

Поле, которого нет в запросе, не меняется. Явный `null` — очистка, допустимая
только для необязательных полей.

Публикация и закрытие выполняются этим же эндпоинтом через `status`:
отдельного эндпоинта раздел 27 не заводит.

```json
{"status": "published"}
```

Допустимые переходы:

```text
draft     → published, closed
published → closed
closed    → published
```

`published → draft` — `409`: по опубликованной вакансии уже могли прийти
отклики, и «черновик с откликами» ничего не означает. Чтобы перестать
набирать, вакансия закрывается. Перевод в тот же статус ошибкой не является.

Для публикации обязательны (раздел 29): `title`, `location`, `schedule` и
зарплата — достаточно одной из границ `salary_min` / `salary_max`.

`criteria` и `questions` заменяются **целиком**: форма вакансии присылает
набор условий полностью. Замена вопросов запрещена, если по вакансии уже есть
отклики: она удалила бы вопросы, а каскадом и сохранённые ответы кандидатов
(раздел 83). Условия менять можно всегда — карточка работодателя показывает
снимок, сделанный на отборе.

Response 200: объект вакансии.

Errors:

```text
401 unauthorized                      — нет сессии
403 wrong_role                        — роль не employer
404 vacancy_not_found                 — вакансии нет либо она чужая
409 invalid_vacancy_status_transition — details: {"status": ..., "target": ...}
409 vacancy_has_applications          — замена вопросов при существующих откликах
422 vacancy_incomplete                — публикация без обязательных данных
422 salary_range_invalid              — итоговый `salary_min` выше `salary_max`
422 vacancy_criteria_invalid          — условия заполнены неверно
422 screening_questions_invalid       — вопросы заполнены неверно
```

Errors:


## GET /api/vacancies/feed

Auth: `candidate`.

Query: `limit` (1–50, по умолчанию 20), `offset` (≥ 0).

Отдаёт опубликованные вакансии, которым кандидат объективно не противоречит
(раздел 30). Из ленты убираются только вакансии с проваленным **обязательным**
критерием и те, на которые кандидат уже откликнулся. Если критерий проверить
нечем — вакансия остаётся.

Пока профиль кандидата не создан, лента пустая: подбирать не по чему.

Обязательные критерии считаются на стороне приложения, поэтому вакансии
читаются из базы пакетами; выборка проходится целиком, чтобы `total` не
зависел от внутреннего размера пакета.

Response 200:

```json
{
  "items": [
    {
      "id": 12,
      "title": "Бариста в центре",
      "location": "Москва",
      "salary_min": null,
      "salary_max": "90000.00",
      "schedule": "full_time",
      "criteria": [
        {"type": "location", "required": true, "value": {"city": "Москва"}}
      ]
    }
  ],
  "limit": 20,
  "offset": 0,
  "total": 1
}
```

`total` — полное число подходящих кандидату опубликованных вакансий, а не
размер страницы. Следующая страница есть, пока `offset + limit < total`.

Errors:

```text
401 unauthorized      — нет сессии
403 role_not_selected — роль ещё не выбрана
403 wrong_role        — роль не candidate
422 validation_error  — некорректные limit/offset
```

## POST /api/vacancies/{id}/apply

Auth: `candidate`.

Request: тело не требуется.

Создаёт отклик и сразу отправляет его на первичный отбор (раздел 32).

Response 201 — отклик создан этим запросом:

```json
{
  "id": 7,
  "vacancy_id": 12,
  "status": "screening",
  "created_at": "2026-09-22T09:10:00Z"
}
```

Response 200 — отклик уже был: возвращается существующий, с его текущим
статусом. Раздел 57 требует именно вернуть существующий отклик, а не ошибку,
поэтому повтор запроса безопасен и ничего не создаёт (раздел 79). Повтор не
возвращает уже пройденный отбор обратно в `screening`.

Дальше фронт ведёт кандидата на `GET /api/applications/{id}/screening`.

Ограничение частоты: 30 откликов на пользователя за 60 секунд
(`APPLY_RATE_LIMIT_REQUESTS`, `APPLY_RATE_LIMIT_WINDOW_SECONDS`), раздел 78.

Errors:

```text
401 unauthorized         — нет сессии
403 role_not_selected    — роль ещё не выбрана
403 wrong_role           — роль не candidate
404 vacancy_not_found    — вакансии нет
409 vacancy_not_published — вакансия в draft или closed; details.status
429 rate_limited         — превышена частота; details.retry_after_seconds
```

Профиль кандидата для отклика не требуется: раздел 32 такой проверки не
содержит. Без профиля лента пуста, поэтому обычным путём до отклика не дойти,
но прямой вызов API пройдёт — и отбор тогда не сможет проверить ни один
критерий по профилю.

## GET /api/applications/{id}/screening

Auth: `candidate`, отклик должен принадлежать текущему пользователю.

Вопросы первичного отбора по отклику и уже сохранённые ответы. **Эндпоинта
чтения вопросов в разделе 27 тех-доки нет** — он добавлен как минимально
необходимый источник данных для экрана `Screening` (раздел 61). Если продукт
решит иначе, менять контракт нужно до интеграции frontend.

Response 200:

```json
{
  "application_id": 7,
  "vacancy_id": 12,
  "status": "screening",
  "can_submit": true,
  "questions": [
    {
      "id": 31,
      "question": "Есть ли действующая медкнижка?",
      "type": "boolean",
      "required": true,
      "sort_order": 1,
      "rules": {}
    },
    {
      "id": 32,
      "question": "Сколько месяцев вы работали по этой специальности?",
      "type": "number",
      "required": true,
      "sort_order": 2,
      "rules": {"min": 0, "max": 600}
    },
    {
      "id": 33,
      "question": "Какой график вам подходит?",
      "type": "choice",
      "required": true,
      "sort_order": 3,
      "rules": {"options": ["full_time", "part_time"]}
    }
  ],
  "answers": []
}
```

`can_submit` — отбор ещё не пройден. После прохождения он `false`, а `answers`
содержит сохранённые ответы: экран результата собирается из них.

`rules` — только то, что нужно, чтобы отрисовать поле и проверить ответ до
отправки: `options`, `min`, `max`, `min_length`, `max_length`. Отсекающее
условие вакансии (`must_equal`, см. ниже) сюда не попадает намеренно — зная
его, ответ можно подогнать.

Errors:

```text
401 unauthorized            — нет сессии
403 role_not_selected       — роль ещё не выбрана
403 wrong_role              — роль не candidate
404 application_not_found   — отклика нет либо он чужой
```

## POST /api/applications/{id}/screening

Auth: `candidate`, отклик должен принадлежать текущему пользователю.

Отбор проходится **одним запросом целиком**: сохранения по одному вопросу нет.

Request:

```json
{
  "answers": [
    {"question_id": 31, "value": true},
    {"question_id": 32, "value": 24},
    {"question_id": 33, "value": "full_time"}
  ]
}
```

Правила ответа по типу вопроса:

| `type` | Допустимое `value` | Проверка |
|---|---|---|
| `text` | строка | `min_length`, `max_length` (жёсткий предел 2000 символов) |
| `number` | число или число строкой (`"24"`) | `min`, `max`; `true` числом не считается |
| `boolean` | строго `true` / `false` | — |
| `choice` | строка из `options` | сравнение без учёта регистра и пробелов |

Необязательный вопрос можно не передавать вовсе; `null` и пустая строка равны
«нет ответа». Обязательный вопрос без ответа — ошибка.

Response 200:

```json
{
  "application_id": 7,
  "status": "passed",
  "failed_criteria": [],
  "failed_questions": []
}
```

`status` — `passed` либо `hard_filter_failed`; других значений эндпоинт не
возвращает. Перевод в `under_review` относится к работе работодателя.

`failed_criteria` — типы обязательных критериев вакансии, которым кандидат
точно не отвечает по профилю. `failed_questions` — идентификаторы вопросов,
ответ на которые не прошёл отсекающее условие. Числа, веса и объяснение
подбора — P1 (раздел 64).

Errors:

```text
401 unauthorized                — нет сессии
403 role_not_selected           — роль ещё не выбрана
403 wrong_role                  — роль не candidate
404 application_not_found       — отклика нет либо он чужой
409 screening_already_completed — отбор уже пройден, details.status — текущий статус
422 unknown_question            — вопрос не относится к этой вакансии
422 duplicate_answer            — ответ на вопрос передан дважды
422 screening_answers_invalid   — ответы не проходят проверку формата
```

`422 screening_answers_invalid` перечисляет **все** проблемные поля сразу,
чтобы форма подсветила их за один запрос:

```json
{
  "error": {
    "code": "screening_answers_invalid",
    "message": "Ответы первичного отбора заполнены неверно",
    "details": [
      {"question_id": 31, "code": "boolean_expected"},
      {"question_id": 32, "code": "number_too_large", "details": {"max": 600}}
    ]
  }
}
```

Коды проблем: `answer_required`, `text_expected`, `text_too_short`,
`text_too_long`, `number_expected`, `number_too_small`, `number_too_large`,
`boolean_expected`, `choice_expected`, `choice_not_allowed`.

Важно различать два исхода: нарушение формата — это `422` и отклик остаётся в
`screening`; корректный ответ, не прошедший условие вакансии, — это `200` со
статусом `hard_filter_failed`.

## GET /api/employer/vacancies/{id}/candidates

Auth: `employer`, вакансия должна принадлежать текущему пользователю.

Query: `limit` (1–50, по умолчанию 20), `offset` (≥ 0).

Кандидаты вакансии, прошедшие первичный отбор. Отклики в `created`,
`screening` и `hard_filter_failed` в список не попадают: обязательная
фильтрация на то и нужна, чтобы работодатель их не разбирал. Кандидат с уже
принятым решением из списка не исчезает — у него меняется `status`, поэтому
после решения список достаточно перезапросить.

Порядок — от новых откликов к старым, как в ленте.

Response 200:

```json
{
  "items": [
    {
      "application_id": 7,
      "status": "passed",
      "applied_at": "2026-09-22T09:10:00Z",
      "desired_role": "Бариста",
      "city": "Москва",
      "salary": "70000.00",
      "schedule": "full_time",
      "experience_months": 24,
      "available_from": "2026-10-01",
      "screening_answers": [
        {
          "question_id": 31,
          "question": "Есть ли действующая медкнижка?",
          "type": "boolean",
          "value": true
        }
      ],
      "hard_filters": [
        {"type": "schedule", "required": true, "passed": true},
        {"type": "certificate", "required": true, "passed": null}
      ],
      "explanation": {
        "matched": ["schedule"],
        "experience": {"candidate": 24, "required": 12}
      }
    }
  ],
  "limit": 20,
  "offset": 0,
  "total": 1
}
```

Состав карточки задан разделом 34: только рабочие факторы. **Имени, фамилии и
фото кандидата в карточке нет** — их не перечисляет ни раздел 34, ни
продуктовое ТЗ (п. 4.4). Анонимная карточка как отдельная функция — P1
(раздел 63), но в P0 скрывать уже нечего.

**P1 (разделы 64, 65).** Список отсортирован ranking: сначала кандидаты с
большим весом совпавших желательных (`required: false`) критериев, при
равенстве — как раньше, от новых откликов к старым. Само число веса наружу не
отдаётся — раздел 21 продуктового ТЗ прямо запрещает показывать проценты и
магические числа, поэтому единственное числовое поле подбора — `experience`.

`explanation.matched` — типы критериев (обязательных и желательных), которым
кандидат соответствует; `experience` в этот список не входит и всегда
выделяется отдельно парой чисел. `explanation.experience` — `null`, если у
вакансии нет критерия `experience`: сравнивать не с чем. Веса критериев
берутся текущие (`vacancy_criteria.weight`), а не снятые на отборе: ranking —
это сортировка отображения, а не часть решения о допуске, которое остаётся
неизменным снимком `hard_filters`. Критерий без явного веса считается равным
`1` (настройка весов работодателем — P2, раздел 66).

`city` — город кандидата. Раздел 34 называет это поле «location», но в профиле
и в `GET /api/candidate/profile` оно называется `city`; в карточке оставлено
имя из профиля, чтобы фронт не сопоставлял два названия одного поля.

`hard_filters[].passed`: `true` — подходит, `false` — не подходит,
`null` — проверить нечем (нужных данных нет в профиле либо значение критерия
в неизвестном формате). `certificate` в P0 всегда `null`: он подтверждается
ответом на первичном отборе, а не профилем. Чисел и весов карточка не
раскрывает — развёрнутая объяснимость относится к P1 (раздел 64).

Результат — **снимок, сделанный на первичном отборе**, он хранится в
`applications.hard_filter_result` и позже не пересчитывается. Кандидат прошёл
отбор — работодатель видит его прошедшим, что бы кандидат ни менял в профиле
потом.

Поля профиля в карточке при этом живые: работодатель связывается с человеком,
а не со слепком на момент отбора. Поэтому возможна пара вида
`schedule: "night"` рядом с `hard_filters: schedule passed = true` — это не
ошибка, а разные вещи: текущие данные кандидата и условия, по которым он был
допущен.

Если профиля нет, поля профиля приходят как `null` — список из-за этого не
ломается.

Errors:

```text
401 unauthorized      — нет сессии
403 role_not_selected — роль ещё не выбрана
403 wrong_role        — роль не employer
404 vacancy_not_found — вакансии нет либо она чужая
422 validation_error  — некорректные limit/offset
```

## POST /api/applications/{id}/decision

Auth: `employer`, вакансия отклика должна принадлежать текущему пользователю.

Request:

```json
{"action": "invited"}
```

```json
{"action": "rejected", "reject_reason": "experience"}
```

`action`: `invited`, `rejected` или `reserved` (P1, функция «Резерв», раздел
20). `reject_reason` необязателен и допустим только вместе с `rejected`;
значения — `experience`, `salary`, `schedule`, `location`, `available_from`,
`other` (раздел 20). Сбор причины отказа в UI — функция P1, поле остаётся
необязательным и на backend.

Response 200:

```json
{
  "application_id": 7,
  "status": "mutual_interest",
  "action": "invited",
  "reject_reason": null,
  "match_id": 3,
  "decided_at": "2026-09-22T10:00:00Z"
}
```

```json
{
  "application_id": 8,
  "status": "rejected",
  "action": "rejected",
  "reject_reason": "experience",
  "match_id": null,
  "decided_at": "2026-09-22T10:00:00Z"
}
```

Допустимые переходы:

```text
passed → invited → mutual_interest   (одна операция)
passed → rejected
passed → reserved → invited → mutual_interest
passed → reserved → rejected
```

Приглашение сразу создаёт взаимный интерес (раздел 36): `invited` — состояние
внутри операции, наружу отклик выходит уже в `mutual_interest`, а `match_id`
возвращается тем же ответом. Отдельного подтверждения от кандидата сценарий не
предусматривает: он выразил интерес откликом. `match_id` нужен frontend, чтобы
перейти к выбору слота (`POST /api/matches/{id}/book`).

`reserved` (P1) — тоже промежуточное решение, а не финальное: из него тем же
эндпоинтом можно позже пригласить или отклонить. Кандидату отправляется
уведомление `application_reserved` (раздел 46). Обратного перехода из
`reserved` в `passed`/`under_review` раздел 62 (доска статусов) не описывает —
решение принимается прямо из резерва.

Решение принимается один раз: повторный запрос по тому же отклику — `409`,
кроме перехода из `reserved`, который допускает ровно одно последующее
решение. Отклик, не прошедший отбор (`screening`, `hard_filter_failed`),
решению не подлежит. Статус `under_review` из раздела 26 в P0/P1 не
возникает — экран, где он различим, это доска статусов, реализация которой не
входит в эту функцию.

Errors:

```text
401 unauthorized                  — нет сессии
403 role_not_selected             — роль ещё не выбрана
403 wrong_role                    — роль не employer
404 application_not_found         — отклика нет либо вакансия чужая
409 invalid_state_transition      — из текущего статуса решение недопустимо;
                                    details: {"status": ..., "target": ...}
409 match_already_exists          — у отклика уже есть взаимный интерес
                                    (расхождение данных, решение не записано)
422 reject_reason_not_applicable  — причина отказа передана не с `rejected`
422 validation_error              — неизвестное действие или причина отказа
```

## POST /api/vacancies/{id}/slots

Auth: `employer`, вакансия должна принадлежать текущему пользователю.

Один запрос — один слот. Пакетное создание тех-докой не описано: чтобы завести
несколько интервалов, frontend вызывает эндпоинт несколько раз.

Request:

```json
{
  "starts_at": "2026-10-01T12:00:00+03:00",
  "ends_at": "2026-10-01T13:00:00+03:00"
}
```

Время принимается **только со смещением** (`Z` или `+03:00`). Значение без
смещения — `422 validation_error`: в каком поясе назначено собеседование,
угадывать нельзя. Backend хранит и возвращает время в UTC.

`employer_id` в теле не принимается: работодатель берётся из сессии.

Response 201:

```json
{
  "id": 12,
  "vacancy_id": 4,
  "starts_at": "2026-10-01T09:00:00Z",
  "ends_at": "2026-10-01T10:00:00Z",
  "status": "available"
}
```

Проверки интервала:

```text
ends_at > starts_at
starts_at в будущем
длительность от 5 минут до 8 часов
нет пересечения с действующими слотами этого работодателя
```

Границы длительности — вне тех-доки (раздел 22 описывает только начало и
конец); они заданы настройками `INTERVIEW_SLOT_MIN_DURATION_MINUTES` и
`INTERVIEW_SLOT_MAX_DURATION_HOURS`. Пересечения проверяются по всем вакансиям
работодателя: два собеседования одновременно один человек не проведёт. Слот,
начинающийся ровно в момент окончания предыдущего, пересечением не считается.
Отменённый слот новый не блокирует.

Errors:

```text
401 unauthorized          — нет сессии
403 role_not_selected     — роль ещё не выбрана
403 wrong_role            — роль не employer
404 vacancy_not_found     — вакансии нет либо она чужая
409 slot_overlaps         — пересечение; details: {"slot_id": ..., "vacancy_id": ...}
422 slot_interval_invalid — конец не позже начала
422 slot_in_past          — начало в прошлом
422 slot_too_short        — details: {"min_minutes": 5}
422 slot_too_long         — details: {"max_hours": 8}
422 validation_error      — время без смещения или не разобрано
```

## GET /api/vacancies/{id}/slots

Auth: `employer` или `candidate` — раздел 37 описывает один эндпоинт на обе
стороны, состав ответа зависит от того, кто спрашивает.

Работодатель (владелец вакансии) видит **все действующие** слоты, включая
занятые: ему нужна своя занятость целиком. Отменённые не показываются никому.

Кандидат видит только то, что можно выбрать: слоты `available`, время которых
ещё не прошло. Доступ открывается **после взаимного интереса** по этой
вакансии — иначе `403 match_required`.

Response 200 (кандидат):

```json
{
  "vacancy_id": 4,
  "items": [
    {
      "id": 12,
      "vacancy_id": 4,
      "starts_at": "2026-10-01T09:00:00Z",
      "ends_at": "2026-10-01T10:00:00Z",
      "status": "available"
    }
  ],
  "match_id": 3,
  "interviews": []
}
```

Response 200 (работодатель): те же `items` (плюс занятые слоты со
`status: "booked"`), `match_id` всегда `null`, а `interviews` — все
назначенные собеседования по этой вакансии.

`match_id` — с чем идти в `POST /api/matches/{id}/book`.

`interviews` — уже назначенные собеседования: кандидату возвращается только
его собственное (ноль или одно), работодателю — все по вакансии. Это источник
данных для экрана «Интервью назначено» после перезагрузки Mini App и для связи
«слот ↔ отклик» у работодателя. Занятый слот кандидату в `items` не попадает —
своё время он видит только здесь. Личных данных кандидата в ответе нет
(раздел 34): собеседование ссылается на отклик.

Формат элемента `interviews`:

```json
{
  "id": 5,
  "match_id": 3,
  "application_id": 7,
  "vacancy_id": 4,
  "slot": {
    "id": 12,
    "vacancy_id": 4,
    "starts_at": "2026-10-01T09:00:00Z",
    "ends_at": "2026-10-01T10:00:00Z",
    "status": "booked"
  },
  "status": "scheduled",
  "application_status": "interview_scheduled",
  "created_at": "2026-09-22T10:05:00Z"
}
```

Слоты отсортированы по времени начала.

Errors:

```text
401 unauthorized      — нет сессии
403 role_not_selected — роль ещё не выбрана
403 match_required    — кандидат без взаимного интереса по этой вакансии
404 vacancy_not_found — вакансии нет; для работодателя — ещё и чужая вакансия
```

## DELETE /api/vacancies/{id}/slots/{slot_id}

## POST /api/ai/parse-vacancy (P1)

Auth: `employer`.

Вспомогательный эндпоинт под создание вакансии (раздел 58): разбирает
свободный текст в черновик полей. **Ничего не создаёт и не публикует** —
работодатель правит черновик на экране подтверждения (продуктовое ТЗ, п.
5.1) и отправляет уже отредактированные данные обычным `POST /vacancies`.

Request:

```json
{"text": "Ищем бариста в кофейню на Тверской, полный день, от 70000"}
```

Response 200:

```json
{
  "parsed": {
    "title": "Бариста",
    "location": "Тверская",
    "salary_min": "70000",
    "salary_max": null,
    "schedule": "full_time",
    "criteria": [
      {"type": "schedule", "required": false, "value": {"schedule": "full_time"}}
    ],
    "questions": []
  },
  "source_text": "Ищем бариста в кофейню на Тверской, полный день, от 70000",
  "provider": "gigachat",
  "ai_available": true,
  "rejected": false,
  "rejection_reason": null
}
```

Все поля `parsed` необязательны и не валидируются на диапазоны — это
подсказка для формы, а не готовые к сохранению данные.

`provider` — какой провайдер ответил (`gigachat` или `yandexgpt`); команда
намеренно держит два провайдера текстовой генерации с отказоустойчивостью
между ними (раздел 57): если первый по порядку (`AI_PROVIDER_ORDER`)
недоступен или перегружен, автоматически пробуется следующий, и это не
видно пользователю, кроме как в значении `provider`.

`ai_available: false` — ни один провайдер не ответил; `parsed` — пустой
объект, frontend переключается на обычную форму вакансии (раздел 57, "AI
unavailable → переход на ручной ввод"). `ai_available: true` при пустом
`parsed` — провайдер ответил, но извлечь поля не удалось (невалидный JSON):
это тоже не ошибка, экран подтверждения просто открывается пустым.

**`rejected` (не из тех-доки, продуктовое требование).** Модель сама
проверяет законность описанной работы по законодательству РФ (промпт прямо
называет проституцию/интим-услуги, оборот наркотиков, работу «закладчиком» и
любую иную запрещённую деятельность) и вместо полей вакансии возвращает
`{"legal": false, "rejection_reason": "..."}`. В этом случае `rejected: true`,
`rejection_reason` — короткое объяснение на русском, `parsed` всегда пустой.
Frontend должен показать причину, а не открывать экран подтверждения.

Важно: это эвристика уровня ИИ, а не техническая гарантия. Она работает
только в этом эндпоинте — прямое создание вакансии через `POST /vacancies`
(ручная форма) содержимое `title`/`description` никак не проверяет.
Отдельно: у самих провайдеров есть собственные встроенные фильтры на
«горячие» темы — сработав, они отвечают не JSON, а обычным текстом отказа;
в этом случае запрос попадает под `ai_available: true` с пустым `parsed`
(как обычный невалидный JSON), а не под `rejected: true` — причина отказа
провайдера в структурированном виде не возвращается.

Errors:

```text
401 unauthorized      — нет сессии
403 role_not_selected — роль ещё не выбрана
403 wrong_role        — роль не employer
422 validation_error  — пустой текст или превышена максимальная длина (4000)
```

## POST /api/ai/transcribe-vacancy (P1)

Auth: `employer`. Тело — `multipart/form-data`, поле `file` (аудио).

Расшифровывает голосовое описание вакансии в текст. Результат передаётся тем
же путём, что и напечатанный текст, в `POST /api/ai/parse-vacancy` — аудио
нигде не сохраняется. Распознаёт только Yandex SpeechKit: это
специализированный сервис речи, а не текстовая LLM, и у GigaChat прямого
аналога нет.

Response 200:

```json
{"text": "Ищем бариста на полный день", "provider": "yandex_speechkit"}
```

`provider: null` и `text: ""` — SpeechKit недоступен (раздел 57): frontend
предлагает ввести текст вручную или напечатать его.

Errors:

```text
401 unauthorized      — нет сессии
403 role_not_selected — роль ещё не выбрана
403 wrong_role        — роль не employer
422 empty_file        — пустой файл
422 file_too_large    — аудио больше 15 МБ
```

## Формат `screening_questions.validation_rules`

Контракт с тем, кто создаёт вопросы вакансии. Тех-дока (раздел 18) описывает
поле как «дополнительные правила проверки ответа», не фиксируя состав.

| Ключ | Для типов | Смысл |
|---|---|---|
| `must_equal` | любой | Отсекающее условие: ответ не совпал — отклик уходит в `hard_filter_failed` |
| `options` | `choice` | Допустимые варианты ответа |
| `min`, `max` | `number` | Диапазон допустимого числа |
| `min_length`, `max_length` | `text` | Длина текста |

`must_equal` — единственный ключ, который кандидату не показывается. Через
него в P0 проверяется обязательный критерий `certificate`: сертификатов в
профиле нет, поэтому наличие документа подтверждается вопросом вида
«Есть ли действующая медкнижка?» с `{"must_equal": true}`.

Отсекающее условие на **необязательном** вопросе не срабатывает, если ответа
нет: проверять нечем. Вопрос с отсекающим условием нужно делать обязательным.

## Формат `vacancy_criteria.value`

Контракт с тем, кто создаёт вакансии: подбор понимает только такие значения.

| `type` | `value` | Как проверяется |
|---|---|---|
| `location` | `{"city": "Москва"}` или `{"cities": ["Москва", "Химки"]}` | город профиля совпадает с одним из указанных, без учёта регистра |
| `schedule` | `{"schedule": "full_time"}` или `{"schedules": [...]}` | график профиля совпадает с одним из указанных |
| `salary` | `{"max": 90000}` | ожидания кандидата не выше потолка; если `max` не задан, берётся `vacancies.salary_max` |
| `available_from` | `{"date": "2026-10-01"}` | кандидат готов выйти не позже этой даты |
| `experience` | `{"min_months": 12}` | опыт кандидата не меньше указанного |
| `certificate` | `{"name": "медкнижка"}` | в P0 по профилю не проверяется: сертификаты в профиле не хранятся, условие подтверждается на первичном отборе |

Числа принимаются и строкой (`"60000"`, `"12"`), и числом. Если значение
указано, но прочитать его нельзя, критерий считается непроверяемым, а не
подменяется другим числом: например, нечитаемый `salary.max` не заменяется на
`vacancies.salary_max`.

Значение неизвестной структуры вакансию из ленты не убирает: подбор считает,
что проверить её нечем. Критерий с `type` вне списка выше (например, от более
новой версии кода) подбор пропускает и в карточке не показывает — лента при
этом продолжает работать.

Подбор использует только поля из раздела 30. Фото, пол, возраст и субъективные
характеристики не используются и в профиле не хранятся (раздел 31).
