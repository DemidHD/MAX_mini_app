# MAX Найм — продуктовое ТЗ (полная версия)

**Версия:** 2.0 · 20.09.2026
**Источник:** `6_MAX_Найм_ТЗ_разработчикам_ПОЛНАЯ_ВЕРСИЯ_v2.docx`
**Назначение:** продуктовое видение и очередь реализации по приоритетам. Технические детали — в [tech-spec-v2.2.md](tech-spec-v2.2.md).

## Главный принцип разработки

Из продукта ничего не выкидываем. Все функции сохраняются в ТЗ. Команда реализует их строго сверху вниз по приоритету. Если времени не хватает — разработка прекращается на текущей точке и сдаётся стабильный верхний слой. Нельзя начинать функцию более низкого приоритета, пока нестабилен более высокий.

Конечный результат обязательного маршрута: **«Интервью назначено»**.

| Слой | Смысл | Правило |
|---|---|---|
| P0 — рабочий маршрут | Минимум, который должен стабильно работать | Без P0 проект не сдаём |
| P1 — ключевая дифференциация | Превращает проект из обычной формы найма в сильный продукт | Делаем сразу после P0 |
| P2 — умный подбор и контроль | Усиливает ценность и демонстрацию | Делаем при наличии времени |
| P3 — рост и зрелый продукт | Масштабирование после основной версии | Не должно мешать P0–P2 |

**Стоп-правило.** Если команда дошла до функции №18 и времени больше нет — функции №19+ не делаем, но они остаются в документации как запланированная часть продукта.

## 1. Назначение продукта

MAX Найм помогает владельцу микробизнеса пройти путь от кадровой потребности до назначенного интервью внутри MAX с минимальным количеством ручных действий.

**Продуктовая формула.** Кандидат свайпает подходящие вакансии. После короткого первичного отбора работодатель получает подготовленную карточку релевантного кандидата и принимает решение одним действием. При взаимном интересе система сразу переводит обе стороны к выбору времени интервью.

**Приоритетный пользователь:** владелец или управляющий микробизнеса с 1–10 сотрудниками; нет отдельного HR или рекрутера; сам принимает решение о найме и ограничен во времени.

**Пилотный контекст:** Москва, HoReCa — бариста, официант, администратор и похожие массовые роли.

## 2. Полный пользовательский сценарий

1. Работодатель открывает MAX Найм и выбирает «Найти сотрудника».
2. Описывает потребность текстом или голосом.
3. Система структурирует вакансию и делит требования на обязательные и желательные.
4. При наличии калибровки работодатель свайпает несколько примеров, чтобы система поняла реальные приоритеты.
5. Вакансия публикуется и получает ссылку / QR для распространения.
6. Кандидат выбирает «Ищу работу», заполняет базовый профиль и видит ленту релевантных вакансий.
7. Кандидат свайпает вакансию вправо — это отклик.
8. Кандидат проходит 3–6 коротких вопросов первичного отбора.
9. Система проверяет объективные обязательные условия.
10. Прошедший кандидат превращается в одинаково оформленную карточку для работодателя.
11. Работодатель свайпает кандидата: отказ / резерв / пригласить.
12. Причина отказа используется как обратная связь для следующих рекомендаций.
13. Если кандидат уже выразил интерес и работодатель приглашает его — возникает взаимный интерес.
14. Кандидат выбирает свободный интервал интервью.
15. Обоим приходит подтверждение в MAX.
16. Кандидат перемещается по простой доске статусов работодателя.
17. Далее система переиспользует ответы, хранит резерв и улучшает порядок выдачи.

## 4. P0 — обязательный рабочий маршрут

### 4.1 Вход и роли
- **Работодатель:** запускает бот / мини-приложение, нажимает «Найти сотрудника».
- **Кандидат:** запускает сервис, нажимает «Ищу работу».
- **Система:** получает идентификатор пользователя MAX, создаёт или находит пользователя, хранит роль и возвращает пользователя в правильный шаг сценария после перезагрузки.

### 4.2 Вакансия
- **Работодатель:** в P0 заполняет форму (должность, город/адрес, зарплата, график, опыт, дата выхода); для каждого условия указывает «обязательное» или «желательное»; видит предпросмотр и публикует.
- **Система:** валидирует поля, создаёт вакансию со статусом «Опубликована», генерирует публичную ссылку.

### 4.3 Профиль и лента кандидата
- **Кандидат:** указывает желаемую роль, город, зарплату, график, опыт и дату выхода; видит подходящие вакансии; может открыть детали.
- **Система:** не требует полного резюме для обязательного сценария; не показывает заведомо несовместимые вакансии, если это проверяется простым правилом.

### 4.4 Отклик и первичный отбор
- **Кандидат:** нажимает «Откликнуться» или свайпает вправо; проходит 3–4 вопроса (график, локация, дата выхода, опыт/сертификат).
- **Система:** создаёт один отклик без дубликатов, сохраняет ответы, проверяет объективные обязательные критерии, показывает корректный статус даже при непрохождении фильтра.

### 4.5 Карточка работодателя
- **Работодатель:** видит стандартизированную карточку кандидата — опыт, ожидания, график, дата выхода, ответы первичного отбора, выполненные условия; нажимает «Отклонить» или «Пригласить».
- **Система:** не показывает псевдоточность вроде «93% идеален», показывает конкретные причины: «5/5 обязательных условий».

### 4.6 Взаимный интерес и интервью
- **Система:** если кандидат уже откликнулся, а работодатель нажал «Пригласить» — создаётся взаимный интерес.
- **Работодатель:** заранее добавляет 2–5 внутренних временных слотов.
- **Кандидат:** после взаимного интереса выбирает один свободный слот.
- **Система:** проверяет доступность слота на момент бронирования, переводит статус в «Интервью назначено», отправляет уведомления обоим в MAX.

## 5. P1 — функции, дающие продукту характер

- **5.1 Разбор вакансии LLM.** Свободный текст → JSON → экран подтверждения с правкой каждого поля. При недоступности модели или невалидном JSON — переключение на P0-форму без потери сценария.
- **5.2 Голосовое создание вакансии.** Голосовое сообщение → транскрипт → тот же механизм, что и у текстового разбора. Аудио дольше необходимого не хранится.
- **5.3 Настоящие свайпы.** Свайп-жест — интерфейсный слой над теми же действиями: вправо — интерес, влево — пропуск/отказ. Кнопки остаются доступным резервным сценарием.
- **5.4 Анонимная карточка.** До взаимного интереса скрыты фото и полное имя; показываются только связанные с работой факторы. После match имя и контакт раскрываются по правилам продукта.
- **5.5 Ранжирование и объяснимость.** Сначала обязательные фильтры, затем простой score по желательным критериям. На экран выводится не процент, а список причин и X/Y совпадений. Формула ранжирования детерминирована и описана в README.
- **5.6 Причина отказа.** Опыт / зарплата / график / локация / дата выхода / другое, одно нажатие. В P1 причина сохраняется, в P2 начинает влиять на рекомендации.
- **5.7 Резерв.** Третье действие работодателя «В резерв»: кандидат не считается приглашённым и не получает match, карточка сохраняется для повторного использования.
- **5.8 Простая доска найма.**

| Колонка | Содержимое |
|---|---|
| Новые | Прошли первичный отбор и ждут решения |
| Взаимный интерес | Match есть, слот ещё не выбран |
| Интервью | Слот назначен |
| Решение | После интервью — ручной финальный статус |

## 6. P2 — умный подбор, удобство и рост

- **6.1 Калибровка предпочтений.** После создания вакансии — 3–5 коротких тестовых профилей с разными компромиссами; быстрые решения работодателя уточняют веса желательных критериев. Пример: если работодатель регулярно выбирает быстрый выход, критерий скорости выхода получает больший вес.
- **6.2 Переиспользование ответов.** Ответы на общие вопросы пишутся в профиль кандидата; на похожей вакансии не спрашиваются повторно, пока актуальны; кандидат может подтвердить или изменить сохранённый ответ.
- **6.3 Разбор резюме.** PDF/DOCX → опыт, роли, навыки, образование, даты. Извлечённые данные всегда подтверждаются кандидатом и не блокируют ручное заполнение.
- **6.4 Персонализация на решениях работодателя.** Используются «пригласить», «резерв», «отклонить» и причина отказа; меняется порядок выдачи среди уже прошедших обязательные фильтры. Нельзя автоматически выводить скрытые чувствительные признаки.
- **6.5 Кадровый резерв.** При создании новой вакансии система сначала проверяет резерв и прошлых подходящих кандидатов — блок «У вас уже есть подходящие кандидаты».
- **6.6 Реферальная механика.** На вакансии есть «Порекомендовать знакомого», создаётся ссылка с идентификатором источника, источник отклика сохраняется для аналитики.
- **6.7 Аналитика.**

| Метрика | События |
|---|---|
| Время до первого интервью | `vacancy_published` → `interview_booked` |
| Конверсия отклика | `vacancy_view` → `application_created` |
| Прохождение первичного отбора | `screening_started` → `screening_completed` |
| Качество фильтра | `application_created` → `hard_filter_passed` |
| Доля взаимного интереса | `candidate_card_viewed` → `match_created` |
| Доля назначенных интервью | `match_created` → `interview_booked` |

## 7. P3 — развитие после хакатонной версии

ИИ-интервью (не как автономное финальное решение), тесты навыков, командный найм, внешний календарь, интеграции с площадками вакансий, документы и адаптация, полноценный ATS.

## 8. Правила сопоставления и фильтрации

**Разрешённые обязательные критерии:** локация / допустимый радиус, график, зарплатные ожидания, дата готовности выйти, минимальный опыт (если он реально обязателен), необходимый сертификат/документ для конкретной работы.

**Нельзя использовать для автоматического решения:** фото и внешность, пол, возраст вне законно обусловленных требований, предполагаемые «харизма», «надёжность», «культурность» и подобные субъективные ярлыки, другие нерелевантные персональные признаки.

**Порядок принятия решения:** обязательные фильтры → ранжирование среди прошедших → объяснимая карточка → финальное решение работодателя.
