# MAX_mini_app — «Навигатор»

Мини-приложение для мессенджера MAX. Хакатон MAX × Минобрнауки, трек 2
«Образовательные решения».

---

## ОБЯЗАТЕЛЬНО ПЕРЕД ЛЮБЫМ ДЕЙСТВИЕМ В РЕПОЗИТОРИИ

Перед первым изменением кода в каждой сессии прочитать целиком три файла в
`docs/`. Это не справочный материал «на всякий случай», а входные требования —
любой код, который им противоречит, считается ошибкой независимо от того,
работает он или нет.

| Файл | Что это | Когда обязателен |
|---|---|---|
| [`docs/TZ_navigator_bot.md`](docs/TZ_navigator_bot.md) | Продуктовое ТЗ: блоки, кнопки, сценарии, логика переходов | Любая работа над экранами, флоу, текстами, доступами |
| [`docs/TZ_tech_stack.md`](docs/TZ_tech_stack.md) | Техническое ТЗ: сервисы, стек, модели данных, эндпоинты, фоновые задачи | Любая работа над бэкендом, БД, API, сборкой, зависимостями |
| [`docs/design_from_claude.md`](docs/design_from_claude.md) | Дизайн-хендофф: 16 экранов, токены, типографика, анимации, состояния | Любая работа над UI, вёрсткой, стилями, анимациями |

**У каждого из трёх файлов есть раздел «Уточнения заказчика» в конце.** Это
ответы на вопросы, которых не было в момент написания ТЗ. Читать обязательно
вместе с основным текстом — часть уточнений отменяет исходные требования.

Исходники дизайна распакованы в [`docs/design/`](docs/design/):
`source/organic-tokens.css` — токены, `source/app.css` — стилизация всех 16
экранов, `source/app.jsx` — логика и контент, который переносится **дословно**
(10 вопросов теста, 15 отписок поддержки). Ничего из этого не сочинять заново.

### Приоритет источников при конфликте

1. **`TZ_navigator_bot.md`** — первичен по функциональности. Если дизайн или
   технический документ расходится с ним по тому, *что* делает продукт,
   прав продуктовый ТЗ.
2. **`design_from_claude.md`** — первичен по внешнему виду и микровзаимодействиям.
   Если продуктовый ТЗ не описывает визуал, а дизайн описывает — делаем как в
   дизайне (пример: метки шанса точками вместо светофора 🟢🟡🔴).
3. **`TZ_tech_stack.md`** — первичен по реализации: стек, границы модулей,
   имена моделей и эндпоинтов.
4. Раздел «Уточнения заказчика» внутри каждого файла **перекрывает** основной
   текст этого файла: это ответы на вопросы, заданные после написания ТЗ.

### Правила работы с этими файлами

- Новые договорённости с заказчиком дописываются **в соответствующий файл в
  `docs/`**, в раздел «Уточнения заказчика», а не в чат и не в отдельные
  заметки. Один раз выясненный вопрос больше не задаётся.
- Файлы в `docs/` изменяются только по решению заказчика. Не «поправить ТЗ под
  реализацию» — наоборот.
- Ссылаться на требования в коммитах и комментариях по номеру пункта
  (например, «ТЗ 1.1 закольцованная навигация»), а не пересказом.

## Рабочие документы: где мы и почему так

`docs/` отвечает на вопрос «что нужно построить» и принадлежит заказчику.
Четыре файла в корне отвечают на вопросы, которых в ТЗ нет и быть не может, и
принадлежат команде — их правит любой разработчик по ходу работы.

| Файл | Отвечает на вопрос | Читать, когда |
|---|---|---|
| [`PLAN.md`](PLAN.md) | Что уже сделано, что следующее, чем оно заблокировано | **В начале каждой сессии, сразу после `docs/`** |
| [`DECISIONS.md`](DECISIONS.md) | Почему код устроен именно так | Перед тем как менять чужое решение или удивиться странному месту |
| [`CONTRIBUTING.md`](CONTRIBUTING.md) | Как здесь принято работать: границы доменов, источники, миграции, тесты | Перед первым коммитом |
| [`README.md`](README.md) | Как это запустить | При первом запуске |

Плюс два источника, которые часто забывают:

- **`git log`** — сообщения коммитов писались как объяснения, а не как ярлыки.
  Если непонятно, зачем сделано изменение, `git log -p` по файлу обычно
  отвечает быстрее чтения кода.
- **README отдельных сервисов** (`apps/*/README.md`) — там лежат ловушки,
  специфичные для конкретного сервиса, и его открытые вопросы.

### Обязанность в конце сессии

Сессии не помнят друг друга — помнит только репозиторий. Поэтому перед тем как
считать работу законченной:

1. **Обновить `PLAN.md`**: статус шага, раздел «Что дальше», открытые вопросы.
   Устаревший план хуже отсутствующего — следующая сессия ему поверит.
2. **Дописать `DECISIONS.md`**, если принято решение, которое не выводится из
   ТЗ и не очевидно из кода. Критерий простой: сможет ли следующий разработчик
   отменить это по незнанию, приняв за случайность.
3. **Ответ заказчика — в `docs/`**, в раздел «Уточнения заказчика». Не в чат.

Незаписанный контекст исчезает вместе с сессией. Записанный — работает на всю
команду.

## Неотменяемые инварианты продукта

Это требования, нарушение которых — блокер приёмки. Проверять на каждом PR.

1. **Закольцованная навигация** (ТЗ 1.1). Тупиковых экранов нет. Кнопка
   `🏠 Главное меню` присутствует на **всех** экранах без исключений,
   реализуется архитектурно через общий layout-роут, а не вручную на каждом
   экране. Покрывается e2e-тестом, обходящим все зарегистрированные роуты.
2. **Кроссплатформенность** (ТЗ 0.2). Мобильный клиент MAX и десктопный/веб
   клиент MAX — одинаково полный функционал, одна кодовая база, адаптивная
   вёрстка, ввод мышью/клавиатурой наравне с touch. Блок не считается готовым,
   пока не проверен на обоих.
3. **Профиль — единственный источник правды** о пользователе (ТЗ 1.3, 3).
   Статус, вуз, группа хранятся в одном месте; остальные блоки только читают.
   На фронте: Zustand не хранит копии серверных данных.
4. **Гейт вместо отказа**. Раздел, недоступный по статусу (блоки 4 и 7), ведёт
   на экран-маршрут с кнопкой в профиль, а не показывает «недоступно».
5. **Сохранение состояния сценариев — с одним исключением**. Черновики
   (баллы ЕГЭ, дедлайны, позиция в списке) переживают выход в меню в рамках
   сессии. Прогресс профориентационного теста — **намеренно нет** (ТЗ 1.3):
   это требование, а не баг.
6. **Только открытые источники данных** (ТЗ 3). Никакого сбора персональных
   документов сверх разовой верификации студента.
7. **Дизайн воссоздаётся пиксель в пиксель** по токенам дизайн-системы Organic.
   Хексы не хардкодятся — переносятся в тему проекта как CSS-переменные.
   Палитра фиксированная: тема мессенджера MAX не применяется, тёмной версии
   нет (уточнение Д6).
8. **Каждый внешний источник данных закрыт интерфейсом** с fixture- и
   реальной реализацией, выбор — конфигурацией. Никаких `if DEMO:` внутри
   доменной логики (уточнение У3).
9. **Рейтинг общеплатформенный, а не по вузам** (уточнение У19). Если в коде
   появляется `vuz_id` рядом с лидербордом или титулом месяца — это ошибка.

## Процесс

- В репозитории работают **несколько разработчиков**. Границы доменов из
  раздела 1.1 технического ТЗ соблюдаются жёстко: домены не импортируют
  модели друг друга, только сервисный слой. Коммиты мелкие и тематические.
- Работа ведётся на ветке, указанной в задании сессии. Не пушить в `main` без
  явного разрешения. Pull request открывается только по явной просьбе.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

Rules:
- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
